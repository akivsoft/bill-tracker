# Development plan

## Current status

- **Phase 1 — Project foundation:** complete. Flutter project, dependencies, Material 3, Riverpod, go_router, safe Supabase startup, initial migration, navigation shell, and placeholder routes are in place.
- **Phase 2 — Core financial data layer:** complete for the local-first data foundation. Drift v2 covers the core financial entities; the v1 upgrade preserves existing records; domain calculations and atomic repository operations cover confirmations, transfers, card activity, loan installments, savings, reconciliation, and reversals. Supabase schema v2 is prepared with RLS and NUMERIC amounts. Full synchronization is not enabled.
- **Phase 3 — Authentication, onboarding, and navigation:** complete. Added local-only entry, optional Supabase email authentication/recovery, guarded onboarding/setup routes, persisted user preferences, five-tab stateful navigation, theme selection, and repository-backed summary screens for the dashboard, bills, wallets, and loans.
- **Phase 3 local schema:** Drift v3 adds persistent app preferences through a versioned migration.
- **Phase 4 — Wallet and account management:** implemented with account creation/editing, linked debit-card handling, active/archive lifecycle, account summaries and filters, manual income/expenses, transfers, reconciliation, credit-card purchases/payments, transaction history, reversals, and transaction-derived balance history. Wallet calculations use integer minor units and the existing Drift repository.
- **Phase 5 — Income and expense management:** implemented expected/planned record creation, editing, cancellation, manual confirmation, recurring templates, category/account/date/amount filters, receipt image attachments, income/expense summaries, reversal actions, and dashboard cash-flow/category totals. Planned items do not update balances until confirmed.
- **Phase 6 — Bills and recurring payments:** implemented bill categories and lifecycle controls, recurring occurrence projection, partial payment confirmation and reversals, skipped periods, payment history, filters and summaries, calendar display, and a separate allocation forecast. Provider/reference/reminder preferences reuse the existing bill configuration field; no schema migration was required. Payday planning was deferred to Phase 8; notification delivery remains out of scope.
- **Phase 7 — Loan management and installment tracking:** implemented multiple loans per provider, installment schedules and edits, partial/backdated repayments with or without wallet deduction, payment reversals, loan status calculation, provider summaries, archive/reopen/cancel controls, lender balance adjustment, and historical payment views. Drift schema v5 allows accountless loan payments and v6 stores total repayment separately. Loan funds are credited only through a separate confirmed disbursement transaction.
- **Phase 8 — Payday planner and financial calendar:** recurring payday schedule setup, pause/resume/archive, in-memory recurrence projections, payday-based planned allocations with period and obligation references, priority and over-allocation forecasts, linking already-received income without a duplicate transaction, and monthly/weekly/daily/agenda calendar projections for income, paydays, bills, loan installments, credit-card due dates, and savings goal targets. Bill, loan, and savings payment workflows update linked allocation fulfillment. Drift v7 adds schedule and allocation planning metadata.
- **Phase 9 — Dashboard and financial analytics:** selectable day/week/month/quarter/year/custom periods, confirmed income and spending with prior-period comparisons, cash-flow trend and category charts, account balances, debt/savings/planned allocation summaries, upcoming obligations, and next payday. Dashboard transaction reads are bounded by date, currency, and recent-item limits; actuals and forecasts are presented separately.
- **Phase 10 — Reports, reminders, and local backup:** filtered transaction reports with PDF/XLSX/CSV sharing, local obligation reminders with deduplication/history, and versioned validated local backup/restore with transactional replacement and relationship checks. Cloud synchronization remains disabled until an authenticated, version-checked financial sync backend and complete schema mapping are available; no financial data is uploaded.
- **Phase 11 — Integration, security, and Android release review:** corrected immediate income/expense transaction ordering and added balance/link/idempotency regression coverage; removed verbose Supabase exception/stack logging and unused biometric/connectivity dependencies and permissions; changed lock-screen reminders to generic text; replaced the default Flutter launcher icon; and configured release signing without a debug-key fallback. Analysis is clean and all 87 automated tests pass. Release AAB compilation succeeds, but the artifact is unsigned because no private upload key is configured. Physical-device testing and Play signing remain required.
- **Cloud sync and full financial workflows:** not implemented. Supabase currently handles authentication only; financial records stay local and are never merged or uploaded automatically.

## Next development phases

1. **Secure cloud synchronization** — explicit opt-in, authenticated version-checked writes, retries, remote conflict review, data mapping, and a sync status surface. Supabase currently provides authentication only.
2. **Android distribution and device QA** — configure a privately managed upload key, verify a signed AAB installation/update path, and run physical-device checks for notifications, deep links, layout, and offline workflows.

## Implementation rules

- Keep screens dependent on repository providers, not Drift queries.
- Reuse integer minor-unit calculation services for all displayed and saved amounts.
- Add a Drift migration and preservation test for every local schema revision.
- Require idempotency keys for operations that may be retried.
- Keep forecasts separate from actual balances and never infer a payment from a due date.
- Enable cloud writes only after the sync adapter and version-checked server operation exist.
